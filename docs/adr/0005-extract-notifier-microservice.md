# ADR-0005: Винесення нотифікатора в окремий мікросервіс доставки

- **Статус:** Прийнято
- **Дата:** 2026-06-07

## Контекст

Застосунок — моноліт: API (HTTP + gRPC), сканер, нотифікатор і клінап живуть
в одному процесі (`cmd/server`), на одній БД і одному Redis. Завдання —
розмежувати домени за принципами модульної архітектури і винести щонайменше
один домен в окремий мікросервіс.

Як bounded contexts напрошуються три домени:

- **Підписки (identity)** — підписатися/підтвердити/відписатися/список.
  Володіє таблицями підписок і репозиторіїв у Postgres. Точки входу — REST і gRPC.
- **Виявлення релізів** — лідер-сканер опитує GitHub, детектить нові релізи,
  розкидає завдання на розсилку. Тримається на Postgres (репо + підписники),
  GitHub-клієнті з кешем і Redis-чергах.
- **Доставка (email)** — нотифікатор тягне завдання з черги, рендерить і
  шле листи, дедупить. **У Postgres не ходить узагалі** — тільки Redis + Mailgun.

## Рішення

Виносимо **домен доставки** (нотифікатор) в окремий мікросервіс. Окремий
Go-модуль/репозиторій зі своїм `go.mod` і деплоєм.

Чому саме нотифікатор — у нього найчистіший шов. Він уже спілкується з рештою
системи **тільки** через Redis-чергу `notifications:pending`, а контракт —
JSON `NotificationJob`. Нуль залежності від БД. Тобто кордон уже існує —
лишається перевести нотифікатор з горутини в моноліті в окремий процес.
Продюсер (API + сканер) лишається продюсером, його чіпати не треба.

### Розглянуті альтернативи

- **Винести сканер (виявлення релізів).** Гарний кандидат: ізолював би GitHub
  і його rate-budget в окремий сервіс. Але сканер читає репозиторії й
  підтверджених підписників **прямо з Postgres** — винести його означає або
  шарити БД між сервісами (shared-database, анти-патерн — два сервіси
  зчіплюються через схему), або будувати на боці підписок новий gRPC read-API
  лише задля цього. Зайва складність зараз. До того ж сканер навряд чи є
  вузьким місцем: один кешований виклик GitHub на репозиторій (TTL 10 хв),
  10k підписників `golang/go` — це **1** виклик, а не 10k. Реальне навантаження
  — це розсилка листів, а не опитування. Лишаємо сканер у моноліті;
  **потенційно гарний кандидат на майбутнє** — коли репозиторіїв стане багато
  й захочеться окремий rate-budget і незалежне масштабування опитування.
- **GitHub-gateway окремим сервісом.** І API (`resolveRepo` сідить тег), і
  сканер кличуть `GetLatestRelease` — спокусливо централізувати rate-limit і
  кеш в одному шлюзі. Але це технічний шлюз, не бізнес-домен, і він додає
  мережевий стрибок на гарячому шляху `subscribe`. Забагато інфраструктури
  для поточного масштабу — кеш у Redis і так робить цю роботу всередині процесу.
- **Розкол API vs воркери.** Поділ за runtime-роллю, а не за доменом: обидва
  сервіси сиділи б на тій самій БД і тій самій бізнес-логіці підписок. Не
  відповідає духу завдання (розмежувати **домени**) і для нашого масштабу —
  перебір.

### Дублювання коду — свідоме

Сервіс доставки тримає власні копії дрібної інфраструктури: транспорт email
(`Sender`/`Message` + Mailgun- і console-бекенди), context-handler логів,
ініціалізацію трейсингу, `urls.Builder` і сам контракт `NotificationJob`.
Це дублювання навмисне, а не недогляд.

Альтернатива — спільний модуль — повернула б саме те зчеплення, якого ми
позбулися винесенням: дві кодові бази в версійному lockstep, спільна точка
змін. Для двох сервісів і ~150 рядків стабільного коду, що майже не
змінюється, ціна спільної залежності більша за ціну копії. Тут DRY свідомо
поступається слабкому зчепленню — кожен сервіс самодостатній і деплоїться
незалежно. Якщо зʼявиться третій споживач або ця інфраструктура почне активно
мінятися — тоді винесемо тонкий спільний модуль (чи `go.work`-воркспейс).

## Наслідки

**Плюси:**
- Чіткий доменний кордон: доставка email стає окремим деплоєм і масштабується
  незалежно — а це і є реальне пропускне вузьке місце (десятки тисяч листів
  на один популярний реліз).
- Контракт уже асинхронний (Redis-черга), тож продюсера переписувати не треба
  — нотифікатор просто перестає бути горутиною в `main` і стає процесом.
- Reliable-черга з ADR-0004 уже дає at-least-once **через процесний кордон**:
  краш сервісу доставки не втрачає завдань, reaper їх поверне. Винесення нічого
  тут не ламає.
- Email-залежність (ключі Mailgun, шаблони листів) виходить з основного процесу
  — менша поверхня в API.

**Мінуси:**
- Контракт черги (назви ключів + JSON `NotificationJob`) тепер треба тримати
  синхронним між двома кодовими базами. Виносимо його в спільний контракт, але
  розбіжність версій — новий клас помилок, якого в моноліті не було.
- Два деплої й дві конфігурації Redis замість одної — більше операційної ваги.
- Redis із внутрішньої деталі стає **жорсткою інтеграційною точкою** між
  сервісами: обидва мусять бачити той самий інстанс.
- Трейси тепер перетинають процесний кордон. Зараз span-и воркерів кореневі
  (див. tracing воркерів) — після винесення варто пропагувати trace context
  через чергу, щоб «підписка → реліз → лист» лишався одним трейсом.
