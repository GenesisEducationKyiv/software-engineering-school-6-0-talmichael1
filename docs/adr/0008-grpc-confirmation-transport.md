# ADR-0008: gRPC для виклику підтвердження (контракт через protobuf/buf), REST лишається

- **Статус:** Прийнято
- **Дата:** 2026-06-23

## Контекст

HW9 ([ADR-0007](0007-orchestrated-saga-subscribe.md)) зробив крок 2 саги підписки
синхронним **REST**-викликом API → Notifier за інтерфейсом `ConfirmationSender`. Тепер
(HW10) мігруємо цей внутрішній синхронний виклик між двома сервісами на **gRPC**:
описуємо контракт у `.proto`, підключаємо `buf` для lint і генерації, лишаємо REST
**поряд** (не видаляємо) і порівнюємо обидві реалізації.

Виклик ідеальний для міграції: гарячий внутрішній RPC у крихкому шляху (саме його
оркестратор компенсує при збої), з чітким запит/відповідь і без потреби в людино-
читабельному HTTP назовні.

## Рішення

Описуємо контракт `confirmation.v1.ConfirmationService` з єдиним unary-методом
`SendConfirmation(SendConfirmationRequest) → SendConfirmationResponse`.

### Розташування контракту й кодогенерація

- `.proto` і згенерований код живуть **у модулі Notifier** (`notifier/proto/confirmation/v1`,
  `go_package` у цьому ж модулі), бо **сервер володіє контрактом**. API імпортує цей
  публічний (не-`internal`) пакет через `require` + `replace ./notifier`. Так жоден
  модуль не лізе в `internal` іншого, а Docker-контексти лишаються простими (контекст
  API вже містить `./notifier`; Notifier імпортує власний пакет без зовнішнього replace).
- Розглянута альтернатива — **окремий proto-модуль** (третій модуль, обидва сервіси
  через replace) — давала б симетричнішу залежність, але це ще один модуль і два
  replace заради одного контракту. Власник-сервер простіший.
- Генерація — через **buf** (`buf.yaml`, `buf.gen.yaml`, локальні плагіни
  `protoc-gen-go`/`protoc-gen-go-grpc`), `buf lint` тримає контракт охайним. Існуючий
  `subscription.proto` лишається на protoc — buf вводимо точково під новий контракт.

### Сервер і клієнт

- **Notifier** піднімає gRPC-сервер на окремому порту (`9092`) **поряд** із REST-ендпоінтом
  (`8082`). Обидва транспорти ходять у **спільний `confirm.Service`** (рендер шаблону +
  відправка + метрика — в одному місці), тож логіка не дублюється, відрізняється лише
  транспортна обгортка й маппінг помилок.
- **API**: `GRPCClient` реалізує той самий інтерфейс `ConfirmationSender`, що й
  `RESTClient`, тож **оркестратор не змінюється**. Транспорт обирається конфігом
  `CONFIRMATION_TRANSPORT` (`grpc` | `rest`, за замовчуванням `grpc`); REST лишається
  доступним для відкату й порівняння.
- **Коди помилок gRPC**: `InvalidArgument` на валідації, `Unavailable` на збої
  email-бекенду. Оркестратор компенсує на будь-який не-OK — так само, як на не-2xx у REST.

## Бенчмарк

Чесне локальне порівняння **одним Go-харнесом** (`make bench-confirmation`,
`notifier/cmd/confirmbench -load`): обидва транспорти обслуговує той самий `Service`
з no-op email-бекендом, навантаження дає один closed-loop пул воркерів із
перевикористанням з'єднань — тож єдина змінна це транспорт, а не інструмент.

Машина: Apple M3 Pro, Go 1.25, 50 воркерів, 200 000 запитів на транспорт.

| Метрика | REST (HTTP/1.1 + JSON) | gRPC (HTTP/2 + protobuf) |
|---|---|---|
| Throughput | ~100–127k req/s | ~123–132k req/s |
| p50 latency | ~290–340 µs | ~330–350 µs |
| p99 latency | ~1.5–2.1 ms | **~0.95–1.05 ms** |
| Байтів на запит | **342 B** (267↑ / 75↓) | **133 B** (95↑ / 37↓) |

**Чому такий результат.** На localhost із крихітним unary-викликом **сирий throughput
це паритет** (у межах шуму на завантаженому ноуті) — Go-шний `net/http` і HTTP/1.1 з
keep-alive надзвичайно швидкі, а накладні HTTP/2-фреймінгу на крихітному повідомленні
з'їдають перевагу мультиплексування. Реальні виграші gRPC тут інші й **стабільні**:
- **Трафік ~2.6× менший** (133 проти 342 B/запит): protobuf кодує поля номерами, а не
  повторює текстові назви як JSON; HPACK стискає HTTP/2-заголовки проти багатослівних
  текстових у HTTP/1.1. На більших payload-ах розрив **зростає** — 2.6× це підлога для
  цього повідомлення з трьох полів, не стеля.
- **Хвіст латентності коротший** (p99 ~1 мс проти ~1.5–2 мс): мультиплексування над
  **одним** з'єднанням дає передбачуваніший tail, ніж пул з'єднань HTTP/1.1.

> Першу (хибну) спробу порівняння робили **різними** інструментами — `ghz` (gRPC) і
> `autocannon` (REST). Це міряло «ghz проти autocannon» незгірш за «gRPC проти REST»
> (різні мови, різна роздільність латентності — autocannon округляв до 1 мс), і давало
> оманливе «REST на 25% швидший». Звідси висновок: крос-інструментальні числа не є
> вердиктом; чесний вимір — спільний харнес. Скрипт `scripts/bench/confirmation.sh`
> (ghz + autocannon) лишаємо як демонстрацію роботи buf-згенерованого gRPC під
> стандартним gRPC-інструментом, із цим застереженням.

## Наслідки

**Плюси:**
- Типізований **schema-first** контракт (`.proto`) з кодогенерацією клієнта й сервера
  замість неявного JSON-контракту; типізовані gRPC-статуси замість HTTP-кодів.
- **~2.6× менше трафіку** на запит (protobuf + HPACK), з ростом розриву на більших
  payload-ах.
- Стабільніший **p99** на одному мультиплексованому з'єднанні замість пулу.
- Транспорт перемикається конфігом без змін оркестратора — REST лишається для відкату.

**Мінуси:**
- Ще один порт і залежність на стороні Notifier; крос-модульний `replace` і додатковий
  рядок `COPY notifier/go.mod` у Dockerfile API заради спільного контракту.
- На localhost із крихітним payload-ом gRPC **не швидший** за сирим throughput —
  обираємо його за контракт, трафік і tail, а не за пікову швидкість тут.
- Дві транспортні реалізації паралельно — трохи більше коду (свідомо, на вимогу
  порівняння й відкату).

Спирається на [ADR-0007](0007-orchestrated-saga-subscribe.md): транспорт кроку 2 саги
тепер має дві реалізації за тим самим інтерфейсом `ConfirmationSender`.
