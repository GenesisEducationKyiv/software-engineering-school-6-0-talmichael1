# System Design Record: GitHub Release Notifier

- **Статус:** Прийнято
- **Дата:** 2026-06-23
- **Повʼязані ADR:** [0001](adr/0001-cache-github-client.md), [0002](adr/0002-concurrent-notifier-workers.md), [0003](adr/0003-consumer-defined-interfaces.md), [0004](adr/0004-reliable-delivery-visibility-timeout.md), [0005](adr/0005-extract-notifier-microservice.md), [0006](adr/0006-rabbitmq-message-broker.md), [0007](adr/0007-orchestrated-saga-subscribe.md)

## Контекст і ціль

Сервіс дозволяє користувачам підписатися на email-сповіщення про нові релізи
GitHub-репозиторіїв. Коли в обраному репо зʼявляється новий тег релізу — усі
підтверджені підписники отримують лист.

**Цілі:**
- Не пропустити жоден реліз (at-least-once доставка).
- Не засипати GitHub запитами (вкластися в ліміт 5000/год з токеном).
- Stateless-інстанси, що безпечно масштабуються горизонтально (лідер-лок на
  сканер, брокер черг розподіляє роботу); доставка масштабується окремо від API.

**Не цілі:**
- Realtime (затримка до 10–30 хв прийнятна).
- Гарантія exactly-once (дублікати в граничних випадках можливі — їх
  гасить дедуп у Redis).

## Архітектура

Система — **два деплойменти**, що спілкуються через RabbitMQ (ADR-0005, ADR-0006):

**API-моноліт** (`cmd/server`) — домени підписок і виявлення релізів:
- **API** — Gin (HTTP) + gRPC. Обробляє підписки, підтвердження, відписки.
- **Scanner** — раз на `SCAN_INTERVAL` (5 хв) інстанс-лідер (Redis-лок) пушить
  репо з активними підписками в чергу `repo_checks`; пул воркерів на будь-якому
  інстансі тягне її і перевіряє нові теги релізів. Stateless, безпечно реплікується.
- **Cleanup** — фоновий воркер (раз на 30 хв): чистить непідтверджені підписки
  старші за годину і реапить саги підписки (ADR-0007).

**Notifier-сервіс** (`notifier/`) — домен доставки, окремий модуль:
- **Notifier** — пул воркерів, що консюмить чергу `notifications` (manual ack) і
  шле листи через Mailgun (ADR-0002, ADR-0006). Залежить лише від RabbitMQ, Redis
  (дедуп) і email-бекенду — без БД, тож масштабується незалежно від API.
- **Confirmation endpoint** — синхронний `POST /internal/confirmations`: учасник
  саги підписки (ADR-0007), рендерить і шле лист-підтвердження. Зараз REST; у HW10
  поряд стане gRPC.

Продюсер (API + сканер) кладе `NotificationJob` у чергу `notifications`, Notifier їх
забирає. JSON-форма завдання — контракт між сервісами.

## Потік даних: scan → notify

1. Лідер циклу (один інстанс на тик — Redis-лок `SET NX EX`) робить SQL JOIN:
   бере тільки репо, де є хоч один підтверджений підписник, і пушить кожне в
   чергу `repo_checks`. Не-лідери пропускають тик — без дублів і гонки на `UPDATE`.
2. Воркери на всіх інстансах тягнуть `repo_checks` (auto-ack) — робота сканування
   розподілена між інстансами. Черга lossy: загублений репо просто перевіриться
   наступного циклу.
3. Кожен воркер тягне `GetLatestRelease` через кешований клієнт (див. ADR-0001).
4. Якщо `release.TagName != repo.LastSeenTag` — формуємо `NotificationJob`
   на кожного підписника і публікуємо по одному persistent-повідомленню в чергу
   `notifications`.
5. `last_seen_tag` оновлюємо **тільки після** успішного enqueue — це дає
   at-least-once: якщо процес помре між enqueue і UPDATE, наступний скан
   повторить.
6. Notifier-воркери (ADR-0002, ADR-0006) консюмлять `notifications` з **manual
   ack**: дворівневий дедуп (перевірка перед відправкою, позначка з TTL після — у
   Redis), потім `Ack`. Невдала відправка — `Nack` назад у чергу; брокер веде
   лічильник спроб (`x-delivery-count`) і обриває ретраї. Неacknowledged-завдання
   мертвого воркера брокер автоматично перевидає — без visibility timeout і reaper.

## Потік даних: підписка (Saga)

Підписка — оркестрована Saga через кордон двох сервісів (ADR-0007). **API —
оркестратор**, **Notifier — учасник**. Виклики синхронні, стан саги — persistent у
Postgres (`subscription_sagas`).

1. Оркестратор створює рядок саги `pending` (журнал на випадок краху).
2. **Крок 1:** створити непідтверджену підписку в Postgres; рядок саги отримує
   `subscription_id` у **тій самій транзакції** (журнал і підписка атомарно узгоджені).
3. **Крок 2:** синхронний REST-виклик `POST /internal/confirmations` Notifier-а →
   рендер і відправка листа-підтвердження.
4. Успіх → сага `completed`. Невдача кроку 2 (не-2xx/таймаут) → компенсація кроку 1
   (видалити підписку), сага `compensated`, користувачу — помилка (чистий ретрай).
5. **Відновлення:** краш між кроками лишає сагу `pending`. Cleanup-реапер робить
   forward-recovery з лімітом спроб: передіслати лист; на успіх → `completed`; при
   вичерпанні `MAX_ATTEMPTS` → компенсувати, `failed`. Старі термінальні рядки GC-иться.

## Сховища

| Що | Де | Чому |
|---|---|---|
| Підписки, репо, токени | PostgreSQL | Реляційні дані, потрібні констрейнти і JOIN. |
| Журнал саги підписки (`subscription_sagas`) | PostgreSQL | Довговічний стан оркестрованої саги; відновлення реапером, ADR-0007. |
| Кеш GitHub-відповідей | Redis (TTL 10 хв) | ADR-0001. |
| Черга нотифікацій `notifications` | RabbitMQ (quorum, persistent, manual ack) | At-least-once доставка через кордон сервісів, ADR-0006. |
| Черга перевірки репо `repo_checks` | RabbitMQ (durable, auto-ack) | Розподіл сканування між інстансами; lossy. |
| Лідер сканера | Redis key `SET NX EX` | Один enqueue-цикл на інтервал поза інстансами. |
| Дедуп надісланих листів | Redis (key з TTL) | Швидко, ідемпотентно. |

## Ключові рішення (підсумок)

- **Кеш GitHub** — Redis із TTL 10 хв (ADR-0001).
- **Concurrent воркери нотифікатора** — пул горутин (ADR-0002).
- **Інтерфейси на боці споживача** — кожен сервіс оголошує рівно той
  набір методів, який реально використовує (ADR-0003).
- **Виділений Notifier-сервіс** — домен доставки винесено в окремий модуль без
  БД, що масштабується незалежно від API (ADR-0005).
- **RabbitMQ як брокер черг** — рідні durable-черги, per-message ack і
  авто-redelivery замість саморобної reliable-черги на Redis; обидві черги
  (`notifications`, `repo_checks`) переїхали в брокер (ADR-0006).
- **Stateless сканер** — лідер на Redis-лоці ставить роботу в `repo_checks`,
  воркери всіх інстансів її розбирають.
- **Брокер як черга, а не таблиця в Postgres** — на масштабі сотень тисяч
  підписників черга-таблиця накопичує мільйони рядків з vacuum-проблемами.
- **Seed `last_seen_tag` при підписці** — щоб новий підписник не отримав
  лист про старий реліз.
- **Оркестрована Saga для підписки** — створення підписки (API/Postgres) +
  лист-підтвердження (Notifier) як розподілена транзакція з persistent-журналом і
  компенсацією; замінює локальний rollback (ADR-0007).

## Ризики і компроміси

- **Більше рухомих частин інфри.** Працюють і Redis (кеш/лок/дедуп), і RabbitMQ
  (черги). Зате семантику черги (ack, redelivery, flow control) тримає брокер, а
  не наш код (ADR-0006).
- **Втрата даних брокера відновна.** Завдання нотифікації ідемпотентні й
  перевиводні: навіть повна втрата черг лікується наступним скан-циклом, який
  перевиявляє реліз і перевиставляє завдання.
- **Mailgun free tier** — 100 листів на добу. Для прод-демо досить.
- **gRPC на Heroku** — Heroku відкриває один порт на dyno, тому gRPC
  доступний лише в Docker-середовищі.
- **Дублікати листів у крайніх кейсах** — якщо процес помер між `email.Send` і
  `MarkSent`, або при ретраї саги підтвердження (ADR-0007). Свідомо обрано
  mark/send-after, бо втратити лист гірше, ніж надіслати дубль; дублі гасить дедуп,
  а посилання-підтвердження стабільне.
- **Синхронна залежність підписки від Notifier-а.** Крок 2 саги — мережевий виклик;
  якщо Notifier недоступний, сага компенсується і користувач ретраїть. Перерване
  виконання підхоплює cleanup-реапер (ADR-0007).
